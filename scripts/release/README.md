# Releasing Superba

The workflows use Rust 1.98. CI checks formatting, runs Clippy and the default
workspace tests on Linux, macOS, and Windows, and builds `spb` in a separate
Linux job without installing GUI packages. Tests use
`SUPERBA_SECRET_BACKEND=file` and `RUST_BACKTRACE=1`; ignored integration tests
are not enabled.

## Release workflow

Ensure that the intended commit has passed CI and that the repository root
contains `README.md`, `LICENSE-MIT`, and `LICENSE-APACHE`. Create and push an
existing-version tag such as `v0.1.0`, or run the Release workflow manually with
that existing tag as the `tag` input. Tags must be `vX.Y.Z` and match
`[workspace.package].version` exactly. Prerelease suffixes are not supported by
this bundle version scheme.

The prepare job resolves the tag to a commit, checks the version and required
documents, and gives every build the same commit. GNU Linux releases build on
Ubuntu 22.04 for its older glibc baseline; the musl release is headless (`spb` and
`superba-router`, no GUI), built by `scripts/release/build-musl.sh` as static PIEs (the
same script runs in CI's `musl` job, on the same image).
macOS builds both architectures with deployment target 11.0, combines them with
`lipo`, and checks that both slices are present. The app bundle requires macOS
11.0 and uses the identifier `com.krill-code.superba`.

| Archive (`<ver>` has no leading `v`) | Contents |
| --- | --- |
| `superba-<ver>-linux-x86_64.tar.gz` | `superba`, `spb`, `superba-router`, release documents |
| `superba-<ver>-linux-aarch64.tar.gz` | `superba`, `spb`, `superba-router`, release documents |
| `spb-<ver>-linux-x86_64-musl.tar.gz` | `spb`, `superba-router`, release documents |
| `superba-<ver>-macos-universal.zip` | `Superba.app` (with `superba-router` in `Contents/MacOS`), universal `spb`, release documents |
| `superba-<ver>-macos-universal.dmg` | the same files; its Finder window shows `Superba.app` and an `Applications` link to drag it onto (see [macOS disk image](#macos-disk-image)) |
| `superba-<ver>-windows-x86_64.msi` | per-user installer: `superba.exe`, `spb.exe`, `superba-router.exe`, `spb-linux-x86_64` (static musl `spb` run inside WSL distributions for session migration), release documents; the only Windows package |

`superba-router` is the opt-in local router. `superba` and `spb` install it as a
per-user service from where they find it: next to themselves (every archive, the
app bundle's `Contents/MacOS`), next to the target of a symlink to them, on macOS
inside a `Superba.app` beside `spb` or in `/Applications` / `~/Applications`, and
finally on the `PATH`. Keep the three programs together when repackaging.

The Windows programs link the C runtime statically (`.cargo/config.toml`), so a
clean Windows needs no VC++ redistributable; the release and MSI jobs run
`scripts/release/check-imports.ps1` on them, which fails when one imports
`VCRUNTIME140.dll`, `MSVCP140.dll` or the UCRT `api-ms-win-crt-*` sets. The GUI
draws with Direct3D 12 on Windows (wgpu; on WARP, the software rasterizer, where
there is no usable GPU, as in VMs without a 3D driver) and with OpenGL elsewhere;
when the window cannot open it says why in a message box and in
`superba-gui.log` in the data directory's `logs` folder.

Release documents are the root README, both license files, `THIRD-PARTY-NOTICES.txt`
(generated by `cargo about` from `about.toml` and
`scripts/release/third-party-notices.hbs`; every license of a linked crate) and,
next to the GUI, `LICENSE-Geist-OFL.txt` (the embedded Geist fonts are OFL-1.1).
`Superba.app` also carries both under `Contents/Resources`. To preview the notices
locally: `cargo install --locked cargo-about --version 0.9.2 --features cli`, then
`cargo about generate --workspace -c about.toml scripts/release/third-party-notices.hbs`.
Linux tarballs
and the macOS ZIP contain a directory matching the archive basename. The DMG
places the listed items at its root (all but `Superba.app` hidden in Finder) next to
the `Applications` link. The GNU tarball directory
is `superba-<ver>-linux-<arch>/`; the musl directory is
`spb-<ver>-linux-x86_64-musl/`. The GNU tarball also holds `superba.desktop` and
`icons/hicolor/<N>x<N>/apps/superba.png` (16 to 512 px): copy `icons/` to
`~/.local/share/icons/` and the desktop file to `~/.local/share/applications/`
(its action "Open ChatGPT with Superba" runs `superba --launch-chatgpt`).

App icon: two masters with the same artwork. `assets/icon/superba.svg` (the tile
fills 928 of 1024 px, as Windows and Linux icons do) gives `assets/icon/png/superba-<N>.png`
and `assets/icon/superba.ico` (embedded in `superba.exe`/`spb.exe` by each crate's
`build.rs`, and used by the MSI). `assets/icon/superba-macos.svg` puts it on Apple's
macOS icon grid (an 824 px continuous-corner tile at 100,100, the shadow inside the
transparent margin) so Superba is as big as other apps in the Dock, Finder and
Launchpad; it gives `scripts/release/Superba.icns` (16 to 1024 px including @2x,
picked up by `macos-bundle.sh`) and `assets/icon/png/superba-macos-256.png` (the
Dock icon of a superba binary run outside `Superba.app`; inside the bundle the
Dock shows `Superba.icns`). `scripts/icons/render.sh` regenerates all of them with
a pure-Rust renderer (resvg; only cargo needed, output is deterministic); re-run
it and commit the outputs after changing either SVG, and change both SVGs together.
`crates/superba-gui/tests/app_icon_tests.rs` checks that the macOS icons stay on
Apple's grid. `Superba.icns` is also the DMG's volume icon; the DMG's window
background has its own master (see [macOS disk image](#macos-disk-image)).

Build jobs never see signing secrets: they have no environment, no secrets and no
build cache, and hand the unsigned macOS app and Windows binaries to two signing
jobs (`sign-macos`, `sign-windows`). Those run in the `release-signing` GitHub
environment: configure it with required reviewers and store the signing secrets
there, not as repository secrets. The signing jobs run only first-party actions
and this repository's scripts; the one third-party tool in `sign-macos`, dmgbuild
(pinned by hash), runs in its first step, before the unsigned app is downloaded and
before any signing material exists, as WiX in `sign-windows` runs while no key is on
disk. Every third-party action in both workflows is
pinned to a full commit SHA (its version in a comment); update pins deliberately.
Only the final job has `contents: write`.

The final job requires all six packages, generates `SHA256SUMS.txt`, and uses
`GITHUB_TOKEN` to create the release with generated notes and tag
verification. It is created as a draft with every asset attached and then
published: `vX.Y.Z` becomes the latest release, `-alpha.N` / `-beta.N` / `-rc.N`
tags become pre-releases. If a draft release for the tag already exists (an
interrupted run), it replaces its archives and checksums (`--clobber`) and
publishes it; if the release is already published it fails instead of
replacing published assets. Download all assets into one directory to verify them with
`sha256sum -c SHA256SUMS.txt` (or `shasum -a 256 -c SHA256SUMS.txt` on macOS).

## macOS signing configuration

Use a Developer ID Application identity. Configuration comes from environment
variables, optionally augmented by one trusted shell env file sourced with
`set -a`. File selection is, in order: `--env-file PATH`,
`SUPERBA_SIGNING_ENV`, then `.secrets/macos-signing.env` relative to the repository
root if it exists. Assignments in the selected file override existing variables.
`MACOS_SIGNING_P12` and `APPLE_API_KEY_P8` may be relative to the env file, and
an absolute path that does not exist on this Mac falls back to a file with the
same name next to the env file (so a copied `.secrets/` directory works as is). Set `SUPERBA_SIGNING_ENV=/dev/null` to use
only the environment and disable default file discovery, as the workflow does.
Keep env files private and never enable shell tracing or print their contents.

| Variable | Purpose |
| --- | --- |
| `SUPERBA_SIGNING_ENV` | Optional path to the trusted shell env file. |
| `MACOS_SIGNING_IDENTITY` | Required signing identity, e.g. `Developer ID Application: NAME (TEAMID)`. |
| `MACOS_TEAM_ID` | Optional team ID; fallback for `APPLE_TEAM_ID`. |
| `MACOS_SIGNING_P12` | Optional path to an exported signing certificate and private key. |
| `MACOS_SIGNING_P12_BASE64` | Base64 certificate alternative; the path takes precedence. |
| `MACOS_SIGNING_P12_PASSWORD` | Certificate password; an empty password is allowed. |
| `APPLE_API_KEY_ID` | App Store Connect API key ID. |
| `APPLE_API_ISSUER_ID` | App Store Connect API issuer ID. |
| `APPLE_API_KEY_P8` | Path to the API private key. |
| `APPLE_API_KEY_P8_BASE64` | Base64 private key alternative; the path takes precedence. |
| `NOTARY_KEYCHAIN_PROFILE` | Alternative profile previously saved by `xcrun notarytool store-credentials`. |
| `APPLE_ID` | Alternative Apple ID for notarization. |
| `APPLE_TEAM_ID` | Team for Apple ID notarization; falls back to `MACOS_TEAM_ID`. |
| `APPLE_APP_PASSWORD` | App-specific password for Apple ID notarization. |
| `TMPDIR` | Parent directory for private temporary files; falls back to `RUNNER_TEMP`, then `/tmp`. |

Without a P12, signing uses an identity already available in the user's
keychains. With a P12, the script creates a temporary keychain with a random
password, imports the certificate, configures command-line signing access, and
adds that keychain while preserving the user's search list. Its EXIT trap
restores the search list, deletes the temporary keychain, and removes temporary
files on success or failure. The script never deletes caller-provided P12/P8
files. Do not run simultaneous certificate-importing invocations under the same
macOS account because the keychain search list is shared.

Notarization uses the first complete credential set: API key ID + issuer + P8,
then a keychain profile, then Apple ID + team ID + app-specific password. Missing
credentials produce a warning and signing continues. `--require-notarize` makes
missing credentials an error; `--no-notarize` explicitly disables submission.
Those two flags cannot be combined. A rejected or timed-out submission fails the
command, with the Apple submission log printed when a submission ID is available.

The GitHub `sign-macos` job takes these six secrets of the `release-signing`
environment: `MACOS_SIGNING_P12_BASE64`, `MACOS_SIGNING_P12_PASSWORD`,
`MACOS_SIGNING_IDENTITY`, `APPLE_API_KEY_ID`, `APPLE_API_ISSUER_ID`, and
`APPLE_API_KEY_P8_BASE64`. If the P12 secret is empty, the workflow emits a warning
and produces unsigned, unnotarized artifacts, including on forks. If it is set,
the remaining configuration must support signing and notarization; failures
stop the release. The password may be empty for a certificate exported that way.
The unsigned archive comes from a job that ran third-party build code, so the job
first accepts only regular files and directories under the expected top
directory (no links, no `..`), unpacks into a fresh `mktemp -d` directory and
checks the top level against the release layout. The step decodes keys into a
second fresh `mktemp -d` directory with `umask 077` and checks again that the
staging directory holds no links or key files before the ZIP and DMG are made.
An `always()` cleanup
step restores the original search list and deletes temporary keys and any
remaining signing keychains, supplementing the script's traps.

## Local macOS signing

Maintainers keep their signing material out of git in `.secrets/` at the
repository root (git-ignored, together with `*.p12`, `*.cer`, `*.p8` and
`*.env`): the Developer ID certificate exported as a `.p12` and an env file
`.secrets/macos-signing.env` with the variables below. A minimal env file:

```bash
MACOS_SIGNING_P12=developer-id-application.p12   # next to this file
MACOS_SIGNING_P12_PASSWORD='<p12 password>'
MACOS_SIGNING_IDENTITY='Developer ID Application: <Name> (<TEAMID>)'
MACOS_TEAM_ID=<TEAMID>
# Notarization (pick one): App Store Connect API key ...
APPLE_API_KEY_ID=<key id>
APPLE_API_ISSUER_ID=<issuer uuid>
APPLE_API_KEY_P8=AuthKey_<key id>.p8
# ... or a profile saved with `xcrun notarytool store-credentials`:
# NOTARY_KEYCHAIN_PROFILE=superba-notary
```

Never print the file, never commit it, and never paste its values into issues or
logs. To build, bundle and sign a universal app locally (and the DMG, below):

```bash
rustup target add aarch64-apple-darwin x86_64-apple-darwin
for t in aarch64-apple-darwin x86_64-apple-darwin; do
  MACOSX_DEPLOYMENT_TARGET=11.0 cargo build --release --locked -p superba-gui -p superba-cli \
    -p superba-router --target "$t"
done
mkdir -p dist/universal
for b in superba spb superba-router; do
  lipo -create "target/aarch64-apple-darwin/release/$b" "target/x86_64-apple-darwin/release/$b" \
    -output "dist/universal/$b"
done
scripts/release/macos-bundle.sh --binary dist/universal/superba --helper dist/universal/superba-router \
  --version 0.1.0 --out dist/app
scripts/release/macos-sign.sh dist/app/Superba.app dist/universal/spb   # reads .secrets/macos-signing.env
# The DMG, as the release makes it: the signed app, spb and the documents.
cp dist/universal/spb README.md LICENSE-MIT LICENSE-APACHE \
  crates/superba-gui/assets/fonts/LICENSE-Geist-OFL.txt dist/app/
scripts/release/macos-dmg.sh build --staging dist/app --version 0.1.0 \
  --out dist/superba-0.1.0-macos-universal.dmg
scripts/release/macos-sign.sh dist/superba-0.1.0-macos-universal.dmg
```

Run on macOS with Xcode command line tools. The signing script rejects other
operating systems before loading configuration. For example, using credentials
already configured in the environment:

```bash
scripts/release/macos-sign.sh --require-notarize dist/Superba.app dist/spb
scripts/release/macos-sign.sh --no-notarize dist/Superba.app
scripts/release/macos-sign.sh --env-file "$SUPERBA_SIGNING_ENV" dist/Superba.app
```

Each Mach-O file under an app's `Contents/MacOS` is signed before the containing
bundle. Signing uses a secure timestamp and hardened runtime, verifies signatures
strictly, and displays public signature summaries. Entitlements are added only
if `scripts/release/entitlements.plist` exists; Superba needs none by default.

The script accepts apps, bare Mach-O binaries, ZIPs, and DMGs. Apps and bare
binaries are submitted inside temporary ZIPs made with `ditto --keepParent`.
ZIPs are extracted privately, their Mach-O code and app bundles are signed, then
they are repacked with the original top-level layout. After notarization, apps
inside a ZIP are stapled before the ZIP is rebuilt. A DMG's contents must already
be signed before creating it; signing the image only seals the container.

Submissions wait up to 30 minutes and must report `Accepted`. Apps and DMGs are
stapled; ZIPs and bare binaries cannot be stapled. Gatekeeper retrieves binary
tickets online. App and DMG Gatekeeper assessments run afterward and report
failures as warnings. Signing, verification, notarization, and stapling failures
are fatal. In the workflow the app is stapled before ZIP/DMG creation, `spb` is
signed and notarized separately, and the finished UDZO DMG is signed, notarized,
and stapled too. See Apple's
[notarization workflow](https://developer.apple.com/documentation/security/customizing-the-notarization-workflow).

## macOS disk image

Opening the DMG shows a drag-to-install window (user bug 84): 640 x 400 pt under the
title bar (a 640 x 428 pt frame: Finder counts the 28 pt title bar of macOS 14 and 15
in the window size; macOS 26's 32 pt one covers the background's bottom 4 pt), no
toolbar, path bar, sidebar, tab bar or status bar, icon view with 128 pt icons and
14 pt labels; `Superba.app` on the left (icon centre 170,170) and an `Applications`
link to `/Applications` on the right (470,170), a dotted coral arrow between them and
the hint "拖到 Applications 即可安装 · Drag to Applications to install" below, on a
pearl background with a sea-blue glow (the app icon's palette). The volume is named
`Superba <version>` and uses `Superba.icns` as its icon (`.VolumeIcon.icns`). `spb` and
the release documents are at the image's root as before, hidden in Finder (`chflags
hidden`; `ls "/Volumes/Superba <version>"` lists them, the ZIP shows them). With a
background picture Finder draws the window light in dark mode as well, so the labels
stay dark on the light background.

| File | Role |
| --- | --- |
| `packaging/macos/dmg-background.svg` | master of the background, 1 unit = 1 pt of the window; the arrow and the hint follow the icon positions |
| `packaging/macos/dmg-background.png`, `dmg-background@2x.png` | 640x400 (72 dpi) and 1280x800 (144 dpi) renderings, committed; dmgbuild joins them into one multi-resolution `.background.tiff` (`tiffutil -cathidpicheck`), so the window is sharp on Retina displays |
| `packaging/macos/dmg-settings.py` | dmgbuild settings: window, view options, icon positions, Applications link, volume icon |
| `packaging/macos/dmg-requirements.txt` | dmgbuild 1.6.7, ds_store 1.3.3, mac_alias 2.2.3: wheels pinned by sha256 |
| `scripts/release/macos-dmg.sh` | builds and checks the image (below) |
| `scripts/release/macos-dmg-layout.py` | reads an image's `.DS_Store` back and compares it with the settings |
| `scripts/release/test-dmg.sh` | opens the window in Finder and takes screenshots in light and dark appearance (CI) |

`scripts/icons/render-dmg.sh` regenerates both PNGs from the SVG (resvg, like the
icon renderers; output is deterministic). Text is shaped only with the font files it
is given: Geist from `crates/superba-gui/assets/fonts` and Noto Sans CJK SC Regular for
the Chinese line (Debian/Ubuntu `fonts-noto-cjk`, macOS `brew install --cask
font-noto-sans-cjk-sc`, or `SUPERBA_CJK_FONT=<file>`). Re-run it and commit both PNGs
after changing the SVG; change the SVG, the icon positions in `dmg-settings.py` and
this section together.

[dmgbuild](https://github.com/dmgbuild/dmgbuild) writes the `.DS_Store` (window,
view options, icon positions, background alias) directly, so nothing scripts Finder
and the layout is the same on every run. `macos-dmg.sh` (macOS, Python 3.10+, set
`PYTHON` to choose one) installs the pinned wheels into a private venv (`pip
--require-hashes --no-deps --only-binary :all:`) and works in two parts:

- `layout --version X.Y.Z --out LAYOUT.dmg`: dmgbuild makes a read-write image with
  the window, the icon positions, the background, the `Applications` link and the
  volume icon, but none of Superba's files (Finder keys positions by name). The image
  is then read back: `.DS_Store` against the settings, the link, the volume icon and
  its custom-icon flag, both resolutions in the TIFF. It refuses to run while a
  volume of the same name is mounted (the background is found by volume name).
- `finish --layout LAYOUT.dmg --staging DIR --out FILE.dmg`: hdiutil, ditto and
  chflags only. It grows a copy of the layout, copies every entry of `DIR` into it,
  hides all but `Superba.app`, converts it to a compressed UDZO image, runs `hdiutil
  verify` and compares the result with `DIR`: same files, the hidden flags, the
  unchanged `.DS_Store`, the link, and a signature that still verifies when the
  staged app is signed.
- `build --staging DIR --version X.Y.Z --out FILE.dmg` does both; `inspect FILE.dmg`
  prints and checks the layout of any image.

In the release, `sign-macos` runs `layout` as its first step and `finish` in the
signing step in place of the former `hdiutil create -srcfolder`, after the app is
signed, notarized and stapled; the DMG is then signed, notarized and stapled by
`macos-sign.sh --require-notarize` as before, and the ZIP is unchanged. To test the
image without a tag: `gh workflow run ci.yml --ref <branch> -f dmg_only=true`. Its
`dmg-package` job builds an Apple silicon app (ad-hoc signed), stages it as the
release does, runs `layout`, `finish` and `inspect`, and `test-dmg.sh` opens the
window in Finder and keeps screenshots in light and dark appearance (artifact
`dmg-test`); `dmg-finder` repeats the screenshots on macOS 15 and 26
(`dmg-finder-<os>`).

## Packaging helpers

`macos-bundle.sh` is portable to Linux and only performs file operations. Supply
the already-built universal binary; it does not build or sign code itself:

```bash
scripts/release/macos-bundle.sh --binary dist/universal/superba --helper dist/universal/superba-router \
  --version 0.1.0 --out dist/app
```

It creates `dist/app/Superba.app` using `Info.plist.in` and writes `APPL????` to
`Contents/PkgInfo`. Each `--helper` executable is installed next to the main
executable in `Contents/MacOS`. An existing destination app is rejected to prevent stale
files. `--bundle-id` optionally overrides the default identifier. If
`scripts/release/Superba.icns` exists, it is copied and referenced in the plist;
otherwise the icon key is omitted.

```bash
scripts/release/package-linux.sh --target-dir target/x86_64-unknown-linux-gnu/release \
  --version 0.1.0 --arch x86_64 --out dist
scripts/release/package-linux.sh --target-dir target/aarch64-unknown-linux-gnu/release \
  --version 0.1.0 --arch aarch64 --out dist
scripts/release/package-linux.sh --target-dir target/x86_64-unknown-linux-musl/release \
  --version 0.1.0 --arch x86_64 --headless --out dist
```

The Linux helper requires binaries plus all three root documents, installs
executable permissions on binaries, and prints the finished archive's absolute
path. It stages privately and moves a completed archive into the output
directory. Both packaging helpers accept numeric `X.Y.Z` versions without `v`.

## Windows MSI

`packaging/windows/superba.wxs` (WiX v5 with its UI and Util extensions, installed in the
signing job by `scripts/release/install-wix.ps1`: `dotnet tool install --global wix --version
5.0.2`, `wix extension add -g WixToolset.UI.wixext/5.0.2` and `WixToolset.Util.wixext/5.0.2`,
each extension DLL checked against a pinned sha256) describes a per-user MSI
(`Scope="perUser"`, no elevation): `superba.exe`, `spb.exe`, `superba-router.exe`,
`LICENSE-MIT`, `LICENSE-APACHE`, `THIRD-PARTY-NOTICES.txt`, `LICENSE-Geist-OFL.txt`
and `superba-msi.marker` in the install folder (default `%LOCALAPPDATA%\Programs\Superba`),
a Start-menu shortcut "Superba", and that folder appended to the user `PATH` (removed on
uninstall).

Installer pages (`packaging/windows/superba-ui.wxs`, WixUI dialogs with our own folder page):
a double-clicked MSI shows Welcome, the install folder, progress and a finish page that says
where Superba went (Start menu "Superba") with "Launch Superba" checked; Finish then starts
`superba.exe` through the shell with the desktop's non-elevated token (`WixUnelevatedShellExec`).
There is no licence page (MIT/Apache-2.0 need no acceptance; the texts are installed). The
folder page takes any folder the user can write to (`Change...` browses; spaces and non-ASCII
names work) and refuses, before anything is written, network/removable drives, folders that
need administrator rights, and Program Files or the Windows folder (also for an administrator
without UAC: Superba installs and self-updates without elevation). The writability check is
`superba_msi_ca.dll` (`crates/superba-msi-ca`, `CheckInstallFolder`): run as the user from the
page, it creates and removes a probe file in the folder (or a probe folder in the nearest
existing folder above it). It is built with the programs for the MSI's Binary table, checked by
`check-imports.ps1` and signed with them, and never installed; if it cannot run, the folder is
accepted and an unwritable one fails the install, which rolls back. The
chosen folder is stored in `HKCU\Software\Krill\Superba\InstallDir`, found again by `AppSearch`
before an older copy is removed, so updates (double-clicked: the folder page shows it read-only),
repairs, the removal and the self-update's `/passive` install keep it; `INSTALLFOLDER=<dir>` sets
it on the command line. `/passive` and `/quiet` installs show no pages and never start Superba (the
self-update starts the new version itself). Branding: `packaging/windows/superba-dialog.bmp`
(493x312, welcome/finish) and `superba-banner.bmp` (493x58, the other pages), rendered from the
icon master by `scripts/icons/render.sh`.

Languages: one MSI, English pages by default and Simplified Chinese on a Chinese Windows.
`build-msi.ps1` builds the package twice with the same ProductCode (`-culture en-US` / `zh-CN`,
WixUI's culture strings plus `packaging/windows/superba.<culture>.wxl`), embeds the difference
as the language transform `2052` (a substorage of the MSI) and sets the package languages to
`x64;1033,2052`: Windows Installer applies that transform by itself when the user's language
is Chinese (the multi-language MSI layout of the Windows SDK's WiLangId/WiSubStg samples; no
bootstrapper). `msiexec /i <msi> TRANSFORMS=:2052` shows the Chinese pages on any Windows. Keep
the two `.wxl` files in step. The UpgradeCode
`669520BE-07D0-496D-8173-085AA3DEE133` is fixed forever; `MajorUpgrade` (also for the
same version, because pre-releases of one `X.Y.Z` share a ProductVersion) replaces the
installed copy in place and refuses downgrades. `scripts/release/build-msi.ps1` maps the
release version to the numeric ProductVersion (`0.1.0-alpha.2` becomes `0.1.0`) and keeps
the full version in the product name and the ARP comments.

Before the files are removed, a custom action runs `spb router uninstall --quiet`: it
switches Codex back to direct if it still goes through the router (configuration only),
removes the router's login startup entry (also when the uninstaller runs as administrator,
where the rest of that step is refused) and stops every `superba-router.exe` started
from the install folder. During an upgrade it runs with `--keep-service` (it only stops
the process; the update restarts the router).

The MSI is built in `sign-windows` (with `spb-linux-x86_64` from the musl job, which
builds and checks it with `scripts/release/build-musl.sh`: static, x86-64, `--version`
runs; build-msi.ps1 refuses a stage without it), after the three executables are signed (and signed
again as a whole when the optional Authenticode secrets are set; WiX runs while no key is
on disk). Test it without tagging: run the `msi-package` job of CI
(`gh workflow run ci.yml --ref <branch> -f msi_only=true`), which builds the MSI on
`windows-latest` and runs `scripts/release/test-msi.ps1`: per-user install, files,
`spb --version`, `PATH`, Add/Remove Programs, Start-menu shortcut, an upgrade to a higher
version and to a same-`X.Y.Z` pre-release, then uninstall and a check that nothing is left;
then the package languages and the embedded `2052` transform (installed once with
`TRANSFORMS=:2052`), and an install into a folder with a space and Chinese characters that an
update without `INSTALLFOLDER` keeps and the removal empties. The pages themselves need a
desktop: they were checked by hand on Windows 11 (user bug 64).

Self-update on Windows downloads this MSI, verifies it against `SHA256SUMS.txt` and runs
`msiexec /i <msi> /passive` after Superba exits.

## Optional Windows signing

Set `WINDOWS_SIGNING_PFX_BASE64` and `WINDOWS_SIGNING_PFX_PASSWORD` to enable the
Authenticode hook. It selects an x64 `signtool.exe` from the Windows SDK, signs the three
executables and then the MSI with SHA-256 and the RFC 3161 timestamp endpoint
`http://timestamp.digicert.com`, and verifies the signatures. The PFX is removed by an
`always()` cleanup step (and by a `finally` in the MSI signing step). Without the PFX
secret signing is skipped and unsigned binaries are packaged.
